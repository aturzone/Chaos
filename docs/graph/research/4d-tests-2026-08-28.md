# §4d: tests

§4d asks for coverage of what matters, not line count, and gives the question to
ask of each area: **what would a wrong answer look like, and would anything catch
it?** It names two thin spots. **One is half stale, one is real and is now fixed,
and the GPU suite has now actually run for the first time.**

## Thin spot 1: "`network/serve` has no test directory at all"

**Half stale.** There was indeed no `tests/` directory, but the crate had **22
inline tests**, and the specific things §4d lists as unasserted were not all
unasserted:

| §4d says | actually |
|---|---|
| its routing | **true — nothing asserted it** |
| its SSE framing | **already covered**: `an_sse_chunk_is_one_event_with_a_blank_line_after_it`, `a_chunk_escapes_content_that_would_break_the_event` |
| its `/status` shape | **true — nothing asserted it** |

And a third hole nobody had named, which is the one that matters most.

### The key gate had no test at all

`authorised(&Request, Option<&str>)` is a pure function, six lines, and the whole
of the server's access control. **Nothing tested it.**

Ask §4d's question. A wrong answer here is a `/v1/*` endpoint that quietly stops
requiring the key. It produces no error, no log line, and no failing test; on a
node bound to `0.0.0.0` — which is what choosing CORE does — it is the entire
security model gone. Would anything catch it? **No.**

Now covered exhaustively, inline where the private function lives:

- no key configured → everything open (the documented default, safe only because
  the server binds loopback unless told otherwise);
- key configured → the page, the mark, the reader, `/status` and `/health` stay
  open **on purpose**, and all four `/v1/*` routes are gated;
- a query string cannot slip past the prefix check (`/v1/models?stream=true`);
- every header shape a real client sends is accepted — `Bearer k`, `bearer k`, a
  bare `k`, and one with surrounding whitespace;
- and the comparison is **full, not prefix**: `Bearer s3cr3`, `Bearer
  s3cr3t-extra`, `Bearer S3CR3T`, `Bearer `, `""` and `Basic s3cr3t` are all
  refused. A prefix comparison is the difference between a check and a formality.

### Two contracts that span two files each

`network/serve/tests/the_contract.rs` — the directory it never had — asserts the
two things no single file could:

**1. The usage block against the route table.** A route implemented and
undocumented is a feature nobody finds. **This caught a real one immediately:**

```
POST /v1/completions works and the server's own --help does not mention it.
```

`POST /v1/completions` and `POST /v1/embeddings` are implemented **and
unit-tested** and were absent from `chaos-serve`'s own help. Somebody wanting
embeddings from Chaos would have concluded it has none. Both are now in the help,
and the test keeps it that way. `/favicon.ico` and `/mark` are exempt by name — an
alias and a browser's reflex — so adding a third exemption is a deliberate act.

**2. `/status`'s keys against the keys `chaos status` reads.** The CLI parses that
JSON by name, in another crate, with no compiler between them. Renaming
`uptime_seconds` would make the line vanish from `chaos status` and read as "the
node did not report it" rather than as a bug. Six keys asserted.

Source checks rather than a socket, deliberately: starting a server needs a model
on disk, and a test that skips itself when the model is absent asserts nothing on
the machine most likely to break these — which is the next thin spot exactly.

## Thin spot 2: the GPU tests skip, and a skip reports as a pass

`CLAUDE.md` records the failure this caused: **a green "6 passed" for a file whose
two GPU tests never ran once.** Cargo has no third verdict, so a test that returns
early is indistinguishable from one that succeeded.

**Fixed by making the skip loud and offering a way to insist.** Sixteen skip sites
across `device_arithmetic.rs` and `scheduler.rs` now go through one helper:

```
SKIPPED (no GPU): no discrete GPU -- set CHAOS_REQUIRE_GPU=1 to make this a failure
```

and with `CHAOS_REQUIRE_GPU=1` a skip **panics**:

```
CHAOS_REQUIRE_GPU is set and this test cannot run: no discrete GPU
```

CI stays green without it, because every runner is GPU-less and must be.

### And then the GPU suite actually ran

This machine has an RTX 3050 and a Vulkan ggml build exists. Pointing
`GGML_LIB_DIR` at `build-vulkan/ggml/src` with `CHAOS_REQUIRE_GPU=1`:

```
ggml_vulkan: Found 2 Vulkan devices:
  0 = Intel(R) RaptorLake-S Mobile Graphics Controller | uma: 1 | fp16: 1
  1 = NVIDIA GeForce RTX 3050 6GB Laptop GPU | fp16: 1 | bf16: 1 | matrix cores: NV_coopmat2

device_arithmetic   6 passed, 0 failed        in 0.84 s   (0.00 s when skipping)
scheduler           6 passed, 2 ignored       in 0.44 s
  a_flash_attention_graph_schedules            ok   (run alone, as its note says)
  views_across_a_split_are_assigned_a_backend  ok   (run alone)
```

**Fourteen GPU tests run and pass on the card**, including the two the file itself
marks *"aborts the whole binary if the bug reproduces; run alone"* — which do not
reproduce. The wall-clock is the tell: 0.84 s against 0.00 s is the difference
between six tests and six early returns.

**What this does and does not verify.** It verifies the ggml FFI, the device
buffers, the mixed host/device graphs and the scheduler **on a real GPU**. It says
nothing about forward-pass parity: the standing "the device path fails 1 of 8
parity prompts where the CPU path fails none" lives in `chaos-arch` and is
arithmetic, not wiring. That remains open, and this is the layer beneath it now
demonstrably sound.

## Two thin spots §4d did not name

- **`chaos-run` has 8 tests** and is the binary most people type. Its argument
  loop, its REFUSED table and its thread tuning are barely asserted — and §4b's
  flag audit had to read its source with a regex because nothing exposes the
  answer. A test that asserts every REFUSED entry is a real llama.cpp flag, and
  that no flag is both implemented and refused, would have made that audit a
  function call.
- **`chaos-android` has 1 test**, and the tier has never been built here (no SDK).
  That is a known blocker rather than a new finding, but it is the largest
  untested surface in the tree.

Neither is fixed here. Both are named so the next person does not have to find
them.

## What §4d changes

- The **key gate** is tested exhaustively, having had no test at all.
- **`network/serve` has a `tests/` directory**, holding the two cross-file
  contracts that no single file could assert.
- **A real defect fixed**: two working OpenAI endpoints were missing from the
  server's own help, found by the test on its first run.
- **A skip can no longer masquerade as a pass**: `CHAOS_REQUIRE_GPU=1`.
- **The GPU suite ran for the first time** — 14 tests, on the card, all passing —
  which retires "a green run is not a full run" for this crate specifically.
- 936 tests, up from 932.
